1. WHAT THIS PROJECT IS (BIG PICTURE)
--------------------------------------------------------------------------------

LTESniffer is an open-source LTE downlink+uplink sniffer that runs on commodity
Software Defined Radio (SDR) hardware — specifically USRP devices (by Ettus
Research). It captures LTE radio frames from the air and decodes them into pcap
files and JSON event streams.

The project on this machine adds a WEB GRAPHICAL USER INTERFACE (GUI) on top of
the existing LTESniffer C++ binary. The GUI lets an operator:
  - Start/stop/restart an LTE capture without touching the command line
  - Watch live decoded metrics (subframes, DCIs, packet rates, cell info)
  - Browse detected UEs (devices on the LTE network), their RNTIs and identities
  - Manage encryption keys used during live capture
  - Browse, download, and post-process captured pcap files
  - Decrypt captured pcap files after the fact using tshark + PDCP key injection
  - Analyze Timing Advance (UE distance from cell) from pcap files
  - View historical capture logs

The audience is a telecom researcher / security researcher who has physical
USRP hardware and wants to analyze LTE traffic in their lab.

4. HOW THE SYSTEM WORKS (ARCHITECTURE)
--------------------------------------------------------------------------------

The system has three layers:

LAYER 1: LTESniffer C++ binary
  - Receives raw IQ samples from USRP hardware over USB/Ethernet
  - Decodes LTE downlink (and optionally uplink) frames
  - Outputs decoded data in two streams:
    a) A pcap file (standard Wireshark-compatible capture file)
    b) A JSON event stream over a named pipe (FIFO) passed via -J flag
  - Events include: cell found, subframe decoded, UE identity, statistics, logs

LAYER 2: Python FastAPI backend (gui/backend/main.py)
  - Runs as a web server on port 8443 (HTTPS) or 8000
  - Manages the LTESniffer subprocess lifecycle (start/stop/restart)
  - Reads the JSON event FIFO and fans events out to all WebSocket clients
  - Serves a REST API for config, keys, captures, USRP detection, etc.
  - Has a mock mode (LTESNIFFER_GUI_MOCK=1) that generates fake data for UI dev
  - Has a replay mode (LTESNIFFER_GUI_REPLAY=<path>) to replay recorded sessions
  - Handles authentication (session cookies, bcrypt password hashing)
  - Performs post-capture pcap processing via tshark (decrypt, organize)

LAYER 3: React frontend (gui/frontend/src/)
  - Single-page React app served as static files from the backend
  - Connects to the backend via WebSocket (/api/events) for live data
  - Uses an external store (useSyncExternalStore) for fast selective re-renders
  - Calls REST endpoints for config, captures, keys, etc.
  - Built with: React 18, TypeScript, Vite, Tailwind CSS, React Router

DATA FLOW (live capture):
  USRP hardware → LTESniffer binary → JSON FIFO → Python backend
  → WebSocket → React frontend (store.ts reducer) → UI components

DATA FLOW (pcap download/decrypt):
  Browser → POST /api/captures/decrypt → backend calls tshark → returns result

5. THE EVENT PROTOCOL (PROTOCOL.md)
--------------------------------------------------------------------------------

The C++ LTESniffer binary emits newline-delimited JSON to the FIFO. Event types:

  hello     - Emitted once at startup with all CLI args
  log       - Free-form log message (info/warn/error/debug)
  cell      - Cell found: PCI, PRB count, frequency, FDD/TDD mode
  mib       - MIB (Master Information Block) decoded
  sf        - Rich subframe event: DL/UL DCIs with RNTI, MCS, TBS, RB alloc
  sf_tick   - Lightweight per-subframe heartbeat (no DCI detail, keeps UI alive)
  identity  - UE identity discovered: IMSI, M-TMSI, GUTI, UE capability
  stats     - Periodic stats: subframes processed, RNTIs seen, CFO, RSRP, CPU%
  bye       - Final event before clean shutdown
  lifecycle - (backend-injected) started/stopped lifecycle events

Frontend store.ts handles all these events in a single reducer function
(applyEvents) and updates the relevant slices of state. React components
subscribe to only the slice they need, so not every component re-renders
on every event (important since events arrive at up to 1000/s from real LTE).

6. AUTHENTICATION & SECURITY
--------------------------------------------------------------------------------

The GUI uses session-cookie authentication:

  - First run: auto-generates admin credentials (username: admin, random 24-char
    password). Prints the password ONCE to stderr with a banner. Stored as bcrypt
    hash in ~/.config/ltesniffer-gui/auth.json (mode 0600).
  - Login: POST /api/login with username/password. Returns a session cookie.
    Cookie is HttpOnly (no JS access), Secure (HTTPS only), SameSite=Strict.
  - Session TTL: 8 hours idle. In-memory store (sessions lost on restart).
  - Rate limiting: max 10 failed logins per IP per 5-minute window.
  - WebSocket: authenticates via the same session cookie (same-origin auto-sends).
  - All /api/* endpoints require authentication except /api/health, /api/login.
  - TLS: self-signed cert auto-generated in ~/.config/ltesniffer-gui/tls/.

Binding modes (set via LTESNIFFER_GUI_BIND env var):
  - Default: binds to detected LAN IP (for LAN access from laptop/tablet)
  - 127.0.0.1: loopback only (max security)
  - 0.0.0.0: all interfaces (prints a warning)

Security hardening done:
  - LTESniffer binary path allowlisted (prevents arbitrary command injection)
  - keys_file path restricted to safe directories
  - Hex key material redacted from log events before broadcast
  - Config/keys files saved with 0600 permissions
  - FIFO path allowlist (only /tmp/ or ~/ltesniffer-captures/)

To rotate credentials: delete ~/.config/ltesniffer-gui/auth.json and restart.
To set custom credentials on first start: set LTESNIFFER_GUI_USER and
LTESNIFFER_GUI_PASS environment variables.

7. HOW TO START THE GUI (RUNNING THE PROJECT)
--------------------------------------------------------------------------------

Prerequisites:
  - Python 3.10+ with the backend virtualenv at gui/backend/.venv
  - Node.js 18+ for the frontend build
  - The LTESniffer binary compiled at LTESniffer/build/src/LTESniffer
  - tshark (Wireshark CLI) installed: sudo apt install tshark wireshark

Step 1: Start the backend
  cd /home/project44/multi-usrp/LTESniffer/gui/backend
  source .venv/bin/activate
  LTESNIFFER_GUI_BIND=<your-LAN-ip>  python -m uvicorn main:app --host 0.0.0.0 --port 8443 --ssl-keyfile ~/.config/ltesniffer-gui/tls/key.pem --ssl-certfile ~/.config/ltesniffer-gui/tls/cert.pem

  OR more simply, if serve.py exists:
  LTESNIFFER_GUI_BIND=<LAN-ip> python serve.py

  The backend serves the pre-built frontend from gui/frontend/dist/.

Step 2 (OPTIONAL — only if frontend source changed):
  cd /home/project44/multi-usrp/LTESniffer/gui/frontend
  npm install
  npm run build
  (outputs to frontend/dist/, served by the backend)

Step 3: Access the GUI
  Open a browser and navigate to https://<server-ip>:8443
  Accept the self-signed TLS certificate warning
  Log in with admin / <password from startup banner>

For development (frontend hot-reload):
  - Start backend with LTESNIFFER_GUI_DEV=1 environment variable
  - Run: cd frontend && npm run dev
  - Access at http://localhost:5173 (Vite proxies /api calls to backend)

For demo/development without real hardware:
  - Start backend with LTESNIFFER_GUI_MOCK=1
  - This generates synthetic LTE events so all UI components show live data

To replay a recorded session:
  - Start backend with LTESNIFFER_GUI_REPLAY=/path/to/session.jsonl.zst

9. KEY IMPLEMENTATION DETAILS (TECHNICAL NOTES FOR DEVELOPERS)
--------------------------------------------------------------------------------

FRONTEND STATE MANAGEMENT (store.ts):
  The frontend does NOT use React Context for performance reasons. Instead it
  uses a module-level external store with useSyncExternalStore. Components
  subscribe to only the slice they need via the useStore(selector) hook.
  This means a component that shows only cell info does NOT re-render when a
  subframe event arrives (important: real LTE runs at up to 1000 events/sec).

  The store is batched at 15 Hz (FLUSH_HZ=15) using a setTimeout debounce.
  Events queue up in pendingRef between flushes. This is why the UI stays
  responsive even at full LTE event rates.

  The reducer (applyEvents) uses reference equality to avoid creating new
  objects when nothing in a particular slice changed. This is critical for
  the component bail-out optimization.

POST-CAPTURE DECRYPTION (captures.py):
  Background: LTESniffer pcap files use DLT 147 (MAC-LTE-framing). Every frame
  tags UEId=0 (the LTESniffer convention). Wireshark's PDCP-LTE dissector keys
  its per-UE decryption table by UEId, not RNTI.

  The decrypt pipeline:
  1. _rewrite_ueid_eq_rnti(): pure Python pcap byte-rewriter. Sets each frame's
     UEId tag to equal its RNTI tag. This is done without calling tshark so it
     works on any platform. Parses the raw pcap binary format (DLT 147 TLV tags).
  2. Writes a Wireshark UAT string (pdcp_lte_ue_keys) mapping each RNTI to its
     K_RRCenc and K_UPenc keys.
  3. Calls tshark with -o uat:pdcp_lte_ue_keys:... options to dissect with keys.
  4. Returns the decoded verbose text + saves the keyed pcap + .uat sidecar.

  The organize_session() function additionally:
  - Splits the capture into one sub-pcap per C-RNTI (ignoring one-hit ghosts)
  - Tries to recover UE identities from RRC Connection Requests in the pcap
    and from sniffer.log API tables
  - In "auto" key-match mode: probes which key produces the most clean
    RRC/IP decodes for each UE (heuristic using _decode_count())

KEY DERIVATION (keyderiv.py):
  Implements 3GPP TS 33.401 Annex A HMAC-SHA256 key derivation:
    K_ASME + NAS_UL_COUNT → K_eNB → K_RRCenc, K_RRCint, K_UPenc, K_UPint
  The 128-bit keys are the LAST 16 bytes (low 128) of the 256-bit KDF output.
  Pure Python stdlib (hmac + hashlib). Includes self-test against srsRAN vectors.
  To run self-test: python -m keyderiv

TIMING ADVANCE DISTANCE MATH (ta_report.py):
  One TA step = 16 × Ts, where Ts = 1/(15000 × 2048) seconds (LTE sample period)
  One-way distance = 16 × Ts × speed-of-light / 2
  Result: ≈ 78.07 meters per TA step (one-way)
  This is a range ring around the eNB, not a position.
  Without GPS + angle-of-arrival, you cannot get lat/lon — only distance.

MOCK MODE (mock.py):
  MockRunner generates synthetic events: fake cell, fake subframes with random
  RNTIs, fake stats, fake log messages. This lets developers work on the UI
  without any USRP hardware. Start with LTESNIFFER_GUI_MOCK=1.

SESSION RECORDING (recorder.py):
  Every live capture session is recorded to a .jsonl.zst file in
  ~/.local/share/ltesniffer-gui/sessions/. These can later be replayed with
  LTESNIFFER_GUI_REPLAY. This is useful for debugging UI issues and demos.

12. KNOWN LIMITATIONS AND THINGS THAT NEED REAL HARDWARE TO TEST
--------------------------------------------------------------------------------

1. PCAP decryption accuracy:
   - The UEId rewriting is done in pure Python against the DLT 147 frame format.
     It has been logic-checked but not tested against a real LTESniffer pcap
     with known keys. The algorithm is correct per the spec but needs live testing.
   - Key derivation has been self-tested against srsRAN vectors and passes.

2. tshark PDCP-LTE dissection:
   - Confirmed tshark 3.6.2 reads LTESniffer pcaps (2433 packets tested).
   - Full PDCP decryption with -o uat:pdcp_lte_ue_keys has been tested on
     sample captures but the live decrypt workflow needs validation with keys
     from a real connected LTE session.

3. Auto key-match heuristic:
   - The _decode_count() function runs tshark once per (UE, key) combination.
     For a capture with many UEs and many keys, this is slow (O(n×m) tshark calls).
     A real multi-UE capture with 10 UEs and 10 keys = 100 tshark invocations.
     Each call may take 2-10 seconds. This should be warned in the UI.

4. LTE identity recovery in pcap:
   - _rnti_identity_map() uses tshark to find lte-rrc.m_TMSI in RRC Connection
     Requests. This only works if LTESniffer captured the RRC layer (requires
     SRB dissection enabled). With API mode (-z) on, sniffer.log may contain
     identity tables that the code also parses.

5. USRP auto-detect:
   - usrp.py calls uhd_find_devices. This tool is not available in all
     environments. The feature gracefully handles absence.
   - GPSDO probe runs uhd_usrp_probe which opens each device — must NOT run
     while a capture is active (the code already guards against this).

6. ta_report.py:
   - Requires tshark on PATH.
   - Has not been tested against a real LTE pcap that includes RAR TA events.
     The math and tshark field names are correct per LTE spec.

15. HOW THE C++ AND PYTHON CONNECT (THE FIFO PROTOCOL)
--------------------------------------------------------------------------------

When the backend starts LTESniffer, it:
1. Creates a temporary FIFO (named pipe): /tmp/ltesniffer-<uuid>.fifo
2. Launches LTESniffer with the -J <fifo> flag
3. Opens the FIFO for reading (async, using asyncio)
4. Reads lines one by one, parses as JSON, broadcasts to WebSocket clients

The C++ JSONEmitter class (src/include/JSONEmitter.h) writes to this FIFO.
The FIFO is the only inter-process communication between C++ and Python.

The backend also:
- Reads stderr from the LTESniffer process (for raw log lines)
- Monitors the process exit code
- Injects synthetic "lifecycle" events (started/stopped) when the process
  starts or exits, so the frontend knows the capture state

Important: LTESniffer runs under sudo (via a sudoers whitelist) because it
needs raw access to the USRP hardware. The backend itself does NOT run as root.

18. THINGS TO KNOW ABOUT THE HARDWARE (FOR CONTEXT)
--------------------------------------------------------------------------------

USRP (Universal Software Radio Peripheral) by Ettus Research / NI:
  - These are software-defined radios that connect to the computer via USB (B210)
    or Ethernet (X310, N310).
  - They receive and transmit radio signals across a wide frequency range.
  - For LTE downlink sniffing, you need at least one USRP (DL only mode).
  - For DL+UL simultaneous capture (dual USRP mode), you need two USRPs.
  - GPSDO = GPS-Disciplined Oscillator: an add-on that locks the USRP's clock
    to GPS timing. Required for accurate uplink timing in dual-USRP mode.

LTE terminology used throughout the code:
  RNTI    — Radio Network Temporary Identifier (16-bit, identifies a UE session)
  C-RNTI  — Cell-RNTI (0x003D-0xFFF3): the main per-UE identifier
  SI-RNTI — System Information RNTI (0xFFFF): broadcast
  P-RNTI  — Paging RNTI (0xFFFE): paging
  RA-RNTI — Random Access RNTI (0x0001-0x003C): random access procedure
  DCI     — Downlink Control Information (resource allocation grants)
  PDCP    — Packet Data Convergence Protocol (the layer that ciphers user data)
  PRB     — Physical Resource Block (frequency unit in LTE)
  PCI     — Physical Cell Identity (0-503, identifies a cell)
  MIB     — Master Information Block (cell's broadcast config)
  K_ASME  — Master session key (256-bit, derived from AKA procedure)
  K_eNB   — eNodeB key (256-bit, derived from K_ASME + NAS count)
  K_RRCenc — RRC encryption key (128-bit, for control plane)
  K_UPenc  — User Plane encryption key (128-bit, for data plane)
  EEA2    — AES-CTR cipher (most common in LTE)
  EIA2    — AES-CMAC integrity (most common in LTE)
  TA      — Timing Advance (round-trip delay in samples; yields UE distance)
  TBS     — Transport Block Size (bytes per DCI grant)
